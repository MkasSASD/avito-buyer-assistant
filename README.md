# ИИ-помощник покупателя

Проект для хакатона ЮФУ 2026. Помогает подобрать комплект мебели и освещения по обычному текстовому запросу.

Пользователь описывает, что ему нужно. Программа извлекает из переписки основные условия — город, бюджет, категории товаров и требования к характеристикам — а затем ищет подходящие позиции в каталоге.

## Как это работает

1. Программа получает историю сообщений в формате JSON.
2. `src/extractor.py` извлекает из неё параметры запроса с помощью языковой модели.
3. Если для подбора не хватает данных, программа возвращает уточняющие вопросы.
4. `src/matcher.py` отбирает товары из каталога и собирает комплекты.
5. `src/formatter.py` формирует JSON-ответ.

Возможны три результата:

- `ok` — найден один или несколько (до трёх) вариантов комплекта;
- `clarify` — не хватает бюджета, города или категорий, программа задаёт вопросы по каждому недостающему полю;
- `no_match` — все условия известны, но подходящего комплекта в каталоге нет или бюджет слишком мал.

## Что умеет программа

- Разбирать запросы на естественном языке, включая историю диалога: новая реплика заменяет прежнее условие, остальные сохраняются.
- Определять город, бюджет (в том числе нулевой), категории и требования к характеристикам (ширина стола, регулировка высоты кресла, цветовая температура лампы).
- Учитывать строгие («меньше», «шире») и нестрогие («до», «не менее») границы и переводить единицы (метры в сантиметры).
- Запрашивать недостающую информацию.
- Фильтровать каталог по структурированным полям. Если характеристика ограничена, а в объявлении её нет, объявление не подходит.
- Считать итоговую цену кодом, а не моделью.
- Предлагать до трёх вариантов разной стоимости: самый дешёвый, средний и самый дорогой из подходящих (комбинации собираются из 40 самых дешёвых подходящих позиций каждой категории).
- Сообщать, если собрать комплект не удалось.

## Защита от управляющего текста в объявлениях

Название и описание объявления — текст продавца, и он может содержать «инструкции» для помощника. Защита построена так, чтобы такой текст не мог повлиять на результат:

- **Модель не видит каталог.** В запрос к модели попадают только история диалога и справочник городов. Названия и описания объявлений ей не передаются.
- **Источник фактов — структурированные поля.** Город, категория, цена и характеристики берутся только из полей `city_id`, `category`, `price_rub` и `attributes`. Число, названное в описании («ширина 50 см»), не заменяет отсутствующую характеристику: такое объявление при ограничении по ней не подходит.
- **Цена считается кодом.** `total_rub` — сумма `price_rub` выбранных объявлений, бюджет проверяется кодом.
- **Объяснения строятся из структурированных данных.** В `explanation` попадают только тип товара, ID объявления, цена и числовые характеристики; название и описание в ответ не выводятся.

Проверки: тест `test_malicious_description_does_not_change_price` и скрипт `testers/injection_check.py` (см. раздел «Тесты»).

## Как устроен проект

| Файл | Что делает |
| --- | --- |
| `run` | Исполняемая точка входа, запускает `main.py` |
| `main.py` | Принимает запрос, запускает обработку и выводит ответ |
| `src/extractor.py` | Извлекает требования из переписки |
| `src/matcher.py` | Фильтрует товары и собирает комплекты |
| `src/formatter.py` | Формирует ответы `ok`, `clarify` и `no_match` |
| `src/llm_client.py` | Отправляет запросы к API модели, повторяет их при временных сбоях; содержит режим-заглушку |
| `src/config.py` | Читает настройки из переменных окружения и пишет логи в stderr |
| `data/` | Каталог товаров, города и категории |
| `examples/`, `schemas/` | Открытые примеры запросов и ответов, JSON Schema контракта (материалы организаторов) |
| `llm/` | Пример клиента и формата вызова модели от организаторов; решением не используется |
| `testers/test_pipeline.py` | Юнит- и интеграционные тесты на заглушке модели (11 тестов) |
| `testers/edge_check.py` | Граничные сценарии с настоящей моделью (13 сценариев) |
| `testers/injection_check.py` | Проверка защиты от инструкций в объявлениях (5 сценариев) |

## Использование языковой модели и сеть

Модель `google/gemma-4-31B-it` вызывается через API организаторов и используется только для извлечения требований в `extract_requirements` из `src/extractor.py`. Один запуск делает один вызов модели.

Сам подбор выполняется обычным кодом: программа фильтрует каталог, проверяет бюджет и собирает комплекты по структурированным данным.

**Сетевые зависимости.** Единственное внешнее соединение — HTTPS-запрос `POST {LLM_BASE_URL}/chat/completions` к шлюзу организаторов (`workers.dev`). Больше программа никуда не обращается, сторонние Python-библиотеки не используются.

**Ошибки и время.** При временных сбоях (HTTP 429, 502, 503, сетевые ошибки, невалидный ответ модели) запрос повторяется до 4 раз, общий лимит времени на запуск — 100 секунд. Технические сбои не превращаются в `no_match`: описание ошибки пишется в stderr, процесс завершается с ненулевым кодом.

## Установка и запуск

### Требования

- Linux или другая среда с bash (на Windows — Git Bash или WSL), UTF-8.
- Python 3.10 или новее.
- Дополнительные библиотеки Python не нужны — используется только стандартная библиотека.
- Файл `run` должен быть исполняемым. Если право на исполнение потеряно, выполните:

```bash
chmod +x run
```

### Настройка API

Ключ нельзя хранить в репозитории. Программа читает настройки только из переменных окружения (файл `.env` сама не загружает):

| Переменная | Назначение |
| --- | --- |
| `LLM_BASE_URL` | Базовый URL API-шлюза, без `/chat/completions` |
| `LLM_MODEL` | Название модели: `google/gemma-4-31B-it` |
| `LLM_API_KEY` | Индивидуальный ключ от организатора |
| `LLM_USER_AGENT` | Имя клиента латиницей, без пробелов, например `hackathon-team-01/1.0` |

Пример:

```bash
export LLM_BASE_URL="https://sfedu-hackathon-ai-gateway.sfedu-hackathon-ai-gateway.workers.dev/v1"
export LLM_MODEL="google/gemma-4-31B-it"
export LLM_API_KEY="<ваш ключ>"
export LLM_USER_AGENT="hackathon-team-01/1.0"
```

### Запуск

Один вызов обрабатывает один запрос: JSON читается из `stdin`, результат пишется в `stdout`, логи идут в `stderr`. В JSON-запросе должен быть непустой массив `messages`.

```bash
./run --catalog /absolute/path/catalog.json < request.json > response.json
```

Пример на открытых данных:

```bash
./run --catalog data/catalog.json < examples/01-selection/request.json
./run --catalog data/catalog.json < examples/02-clarification/request.json
```

Без `--catalog` используется `data/catalog.json`.

## Локальный запуск без API-ключа

Для отладки можно включить режим-заглушку:

```bash
export LLM_API_KEY=mock
```

В этом режиме вместо обращения к API используется простая эвристика на ключевых словах — `_mock_llm_extract` из `src/llm_client.py`. Она нужна для юнит-тестов и локальной отладки без сети и не заменяет настоящую модель, поэтому для итоговой сдачи и проверки диалога заглушку не используйте.

## Тесты

Все команды запускаются из корня репозитория.

**Юнит- и интеграционные тесты (заглушка модели, без сети):**

```bash
LLM_API_KEY=mock LLM_BASE_URL=http://localhost python3 -m unittest testers.test_pipeline -v
```

**Граничные сценарии с настоящей моделью.** `testers/edge_check.py` запускает `./run` на 13 запросах: границы («не шире метра», «шире 100 см»), единицы измерения, все варианты `clarify`, исправление условий в истории, ответ «15 тысяч» на вопрос о бюджете и бюджет 0. Для ответов `ok` он сверяет город, категории, бюджет, итоговую сумму и ограничения по характеристикам с каталогом.

```bash
python3 testers/edge_check.py
```

**Защита от инструкций в объявлениях.** `testers/injection_check.py` делает копию каталога с «инструкциями» в описаниях и названиях и с заведомо неподходящими объявлениями-приманками, запускает на нём 5 запросов и проверяет, что результат остаётся допустимым, приманки не попадают в ответ, а текст инструкций в ответе не появляется.

```bash
python3 testers/injection_check.py
```

Для двух последних скриптов нужны настоящие значения `LLM_*` (заглушка не подходит), на каждый сценарий делается один вызов модели. Каталог можно указать через `--catalog`.
